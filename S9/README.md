# Session 9 — Browser Comparison Agent + Replay Viewer

A browser-capable agent that completes a **real comparison task on a live, JavaScript-driven
website** and produces a full **replay report**. Built on the Session 8 growing-graph
orchestrator (unmodified); all new behaviour is added through the skill catalogue and the
Browser skill.

**Demo video:** _<add your YouTube link here>_

---

## The task

> **Compare the top trending Python repositories on GitHub this week** — for each, extract the
> repository name, language, total stars, and stars gained this week; then rank the
> fastest-growing one.

This is something Session 8's `web_search` + `fetch_url` **cannot** do: GitHub Trending only
shows the ranked, filtered list **after** you apply the *Language = Python* and *Date range =
this week* filters in the browser. A static fetch returns the page shell, not the data. The
agent has to **interact**.

## Quick start

```powershell
# 1. one-time setup
cd llm_gatewayV9      ; uv sync
cd ..\S9SharedCode\code ; uv sync ; uv run playwright install chromium

# 2. provide a key (gateway reads ..\.env). Gemini free tier is enough:
#    S9\.env  ->  GEMINI_API_KEY=...   (GROQ_API_KEY optional, adds failover)

# 3. one-shot demo: wipes memory, runs the agent (live trace), builds + opens the replay
powershell -ExecutionPolicy Bypass -File .\run_github_demo.ps1
```

The gateway auto-starts on `:8109`. To rebuild a replay for any run:
`cd S9SharedCode\code ; uv run python report.py <session_id>`.

Open the self-contained replay: [`S9SharedCode/replay_s8-1b7d65fe.html`](S9SharedCode/replay_s8-1b7d65fe.html)
(generated by [`report.py`](S9SharedCode/code/report.py)). It contains all eight items below.

### 1. Original user goal
> "Open GitHub Trending and find the top trending Python repositories this week … give name,
> language, total stars, stars gained this week (+ description if shown); then rank the
> fastest-growing one."

### 2. Planner DAG
```
planner ──► browser ──► distiller ──► [auto-critic] ──► formatter
```
A clean 5-node DAG (no loops). Rendered as a status-coloured graph in the report.

### 3. Browser path chosen
**`a11y`** (accessibility-tree layer). The cascade is `extract → deterministic → a11y →
vision`, escalating only when a layer is insufficient. The static `extract` layer was correctly
skipped because the data lives behind interactive filters.

### 4. Browser actions taken (≥3 visible actions ✅)
| Turn | Action | Effect |
|---|---|---|
| 1 | `click(21)` | open the **Language** filter |
| 2 | `type "Python"` + `Enter` | search/select language |
| 3 | `click(22)` | apply filter |
| 4 | `click(24)` | set **Date range = this week** |

**Proof it's interaction, not scraping:** the agent was given the base URL
`https://github.com/trending` and *navigated itself* to
`https://github.com/trending/python?since=weekly` by clicking the filters.

### 5. Screenshots / page-state logs
Per-turn screenshots **and** the accessibility-tree legend the agent reasoned over are embedded

## How it works

All LLM traffic flows through the local **`llm_gatewayV9`** proxy (`:8109`): provider failover
(Gemini → Groq), rate-limit handling, per-agent cost ledger, and the `/v1/vision` endpoint for
the Browser's vision layer. The **orchestrator (`flow.py`) is not modified** — new behaviour is
added only via the skill catalogue (`agent_config.yaml` + prompts) and the Browser skill.

See [`ARCHITECTURE_NOTE.md`](ARCHITECTURE_NOTE.md) for the full design and the fixes made during
integration (planner wiring, browser navigation resilience, critic tuning, memory hygiene).
